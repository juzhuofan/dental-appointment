## 优先修复的问题

### 1. [P1] “关闭排班”会取消已有预约，与后台提示相反

- 触发：对含有待确认或已确认预约的已发布排班点击“关闭”。
- 后台提示说“已存在的预约仍然保留”，但后端对 `CLOSED` 和 `CANCELLED` 都调用取消活动预约逻辑，患者预约会被取消并释放号源。
- 位置：`admin-web/src/views/SchedulesView.vue:57`、`:75`；`backend/src/main/java/com/dental/schedule/service/ScheduleService.java:173`。
- 建议：将关闭定义为只停止新预约，将停诊定义为取消已有预约；同步调整服务端、提示、接口约定和测试。现有 `tests/api.integration.test.mjs:161` 已固化关闭即取消的旧行为，不能只修改提示文案后结束。
- 证据：前后端完整调用链和已有集成测试；本轮没有在真实数据上执行关闭操作。

### 2. [P1] 后端允许姓名与电话为空的就诊人占用号源

- 微信开户会建立姓名、电话为空的默认就诊人。这是允许用户稍后填资料的正常开户行为。
- 创建预约时服务端只检查就诊人是否存在和属于当前账号，未校验姓名、联系电话完整性，随后直接占号并保存空值快照。直接调用预约接口可以绕过小程序的资料校验。
- 位置：`backend/src/main/java/com/dental/user/service/UserService.java:542`；`backend/src/main/java/com/dental/appointment/service/AppointmentService.java:107`；`backend/src/main/resources/mapper/AppointmentMapper.xml:67`。
- 建议：在占号前统一校验真实姓名、手机号，返回明确的资料未完成错误，让小程序跳转完善资料；开户本身继续允许资料留空。
- 证据：实际 `AppointmentService` 配合模拟 Mapper 运行成功，空姓名/电话仍触发占号并生成 `PENDING` 预约；内部复现文件为 `.local/audit-repros/BookingProfileRepro.java`，没有数据库或网络调用。

### 3. [P2] 后台切换预约详情时，旧响应可能覆盖当前记录

- 触发：慢网下打开 A、关闭详情、再打开 B；B 先返回、A 后返回。
- 结果：详情抽屉显示 A，操作按钮也作用于 A，与最后选择的 B 不一致。
- 位置：`admin-web/src/views/AppointmentsView.vue:34`；状态修改后的详情刷新 `:63` 也需同样保护。
- 建议：增加请求序号和当前记录 ID 校验，关闭或切换时使旧请求失效。
- 证据：提取实际 TypeScript 函数并以延迟 Promise 复现；脚本 `.local/audit-repros/admin-detail-race.mjs`。

### 4. [P2] 旧请求的迟到 401 会清空刚建立的新登录状态

- 触发：旧令牌请求尚未结束，用户已重新登录；旧请求随后返回 401。
- 结果：请求层无条件清除当前会话，新的有效令牌和账号资料一起被清空，用户再次被要求登录。
- 位置：`miniapp/src/utils/request.js:35`、`:45`。
- 建议：响应失效处理必须比较该请求的令牌或会话代次，不能让旧会话的响应清除新会话。
- 证据：实际 request/session 模块的内存复现，旧响应到达后新 token 变为空、user 变为 null。

### 5. [P2] AI 历史消息加载失败后的“重新加载”没有重新请求

- 触发：AI 页已经初始化成功，打开另一个历史会话时网络失败，再点重新加载。
- 原因：按钮调用 `activate()`，但该方法因 `initialized` 已为 true 直接返回，错误和空消息仍保留。
- 位置：`miniapp/src/utils/ai-chat.js:30`；`miniapp/src/pages/ai/index.vue:34`。
- 建议：将初始化与当前会话的消息重试分开，失败时重试当前会话。
- 证据：重试前后消息请求次数保持 2，未新增请求。

### 6. [P2] 删除 AI 会话后继续翻页会漏掉历史记录

- 触发：加载前 20 条会话，删除其中一条，再加载下一页。
- 原因：服务端使用偏移分页；删除后后续记录前移，客户端仍从原偏移量继续取，跳过一条记录。
- 位置：`miniapp/src/utils/ai-chat.js:121`、`:138`。
- 建议：删除后刷新已加载分页基线，或改用稳定游标；新建、重新排序也应一并验证。
- 证据：40 条删一条后服务端剩 39 条，客户端只显示 38 条且已无更多入口。问题 4—6 的复现脚本为 `.local/audit-repros/miniapp-edge-cases.mjs`。

### 7. [P2] 一键验证入口已落后于当前登录与测试组织

- `scripts/Verify-Local.ps1:8` 仍运行依赖 `/auth/demo-login` 的旧集成测试，而当前患者登录已采用真实微信身份。`tests/ui/miniapp.spec.mjs:64` 仍等待旧接口和旧按钮文案。
- AI 与账号资料界面测试默认分别连接 6184、6185 端口；标准验证脚本未启动这些隔离预览，也未统一注入预览地址。
- 根目录验证入口未纳入全部现有单元测试，最新的账号资料单元测试还没有对应 npm 脚本。
- 建议：统一隔离测试环境与运行入口，业务流程测试通过测试专用身份边界建立夹具，覆盖本轮缺陷，避免依赖产品开放演示登录。不要为了迁就旧测试重新开放演示登录。
- 证据：脚本与测试配置交叉核对；本轮没有执行会向当前业务库创建数据的旧集成套件。

## 需要明确的业务规则

1. **未到预约时间即可登记完成或爽约。** 前后端当前只检查状态，没有时间门槛；现有集成测试还以未来排班执行这类操作。建议明确允许完成的最早时间、爽约判定时间与管理员纠错机制，再同时约束前后端。位置：`backend/src/main/java/com/dental/appointment/service/AppointmentService.java:236`。
2. **同一就诊人可预约相互重叠的不同排班。** 当前防重键是“就诊人 ID + 排班 ID”，不等于时段冲突检查。是否禁止跨医生重叠、连续项目是否允许，应由门诊使用规则决定。
3. **超过取消截止时间仍展示取消按钮。** 后端会拒绝，数据安全约束仍有效；小程序可提前禁用并显示截止原因、提供联系诊所入口，减少无效操作。位置：`miniapp/src/pages/appointment/index.vue:2`。
4. **预约截止与取消截止共用同一个提前量。** 默认配置下，就诊前 120 分钟既不能取消，也不能新预约。建议确认是否符合诊所规则；若希望允许临近预约，应拆成两项配置，不能只修改界面文字。位置：`backend/src/main/java/com/dental/appointment/service/AppointmentService.java:101`、`backend/src/main/resources/mapper/AppointmentMapper.xml:92`。
